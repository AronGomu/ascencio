1. Findings and scope

  1. Post-evaluation preparation is almost as expensive as the entire old evaluation. The old runner reports 192.83 minutes for 10,000 games. At the snapshot, preparation has consumed 190.11 minutes and generated 4,121 of 5,009 loss views. This is file processing, not analyst reasoning.
  2. The new match and replay writers already avoid a global directory scan per write; analysis does not. Reuse that improvement in analysis publication and report completion. Adding analysts cannot accelerate a preparer that holds the session lock.
  3. The TypeScript coordinator had avoidable serial work at the initial snapshot. During this review, the ongoing migration moved match-finalization verification into engine workers and changed the final tally to read match summaries. These two findings are now implemented in the working tree; their performance still needs verification. The coordinator's resume path still validates completed matches sequentially.
  4. Loss views should be produced from the worker's existing actor records as each completed loss is finalized. Publish their hashes and decision indexes with the evidence. Analysts can still start only after evaluation and the decision finish, preserving the current skill's barrier.

  6. The migration needs an end-to-end performance gate. The saved 144-game native TypeScript comparison is 10.5% faster than optimized Rust; a later 200-game comparison is 52.1% slower. These are small, different tests, not proof of a uniform speedup or regression.

3. What the existing optimizations have achieved

Worker and batch improvements are already real

The saved eight-match comparison with four workers and alternating order measured legacy execution at 21.46 / 20.75 seconds and independent batch execution at 10.24 / 10.17 seconds: about 2.07× throughput from their mean times, with matching gameplay fingerprints. This small test supports the batch optimization; it does not establish sustained 2,500-match performance.

The separate one-minute worker trials measured 5.94 games/s at six workers, 6.40 at eight, 6.70 at ten and 6.74 at twelve. Going from ten to twelve gained only about 0.56% throughput while reported summed RSS rose from 8.99 to 11.49 GB. Those were single sequential trials, not a repeated calibration. They illustrate why “more workers” is no longer the main recommendation.

4. Detailed review and optimization opportunities

4.1 Setup, validation and calibration

Move compatibility failures to preflight. The current validate-candidate.ts handles an unchanged packaged bot.mjs baseline, but still explicitly rejects changed packages without a target-AI-only adapter. A run can therefore spend hours analyzing losses before discovering it cannot validate its resulting package. Preflight both the unchanged baseline path and the supported changed-candidate boundary using tooling fixtures; do not change the evaluated AI for a preflight smoke check.

Freeze executable dependencies once and reuse them. Key compiled variants, content loading and verification by the complete transitive source/content/configuration identity. Keep source identity, runtime identity, administrative resource limits and benchmark identity explicit. Moving from Rust scheduling to TypeScript must create a separately bound execution; do not relabel the active run or treat outcomes from an unverified runtime as interchangeable.

Make effective limits a single machine-readable contract. The skill authorizes 50 GB, five-hour evaluations and the 10% evaluation-recovery allowance, but generic storage defaults still say 20 GB and the experimental replay pool defaults to 30 minutes. Its replay-branch timeout is a separate concept and remains capped at five minutes. Resolve run, evaluation, pool and branch limits explicitly before dispatch; show which limit will stop each operation. This prevents avoidable interruptions and repeated resource questions without silently increasing any bound.

Do not pay for exhaustive calibration on every minor edit. On a 16-logical-CPU machine, the current default 2–16 sweep with two repetitions is 30 stages. At 16 matches per stage, that is 480 matches / 1,920 games, before fingerprint and zero-work-resume verification. typescript-benchmark.ts performs those extra checks on every stage, outside its recorded execution time. Preserve exact current cache validity; proposed future work is a performance-dependency key plus a short revalidation, with full sweep on meaningful runtime/workload changes. An adaptive sweep would require changing the skill's exhaustive-calibration policy, not silently skipping counts.

Calibration should record its full wall time and total output, not just the inner execution times. Run it without competing heavy benchmarks, alternate order, and test enough matches to distinguish startup from sustained throughput. The saved three-match smoke recommendation is a tooling check, not a production choice for a 2,500-match evaluation.

4.2 Evaluation: optimize the TypeScript critical path

Final full-timeline tally: now addressed in the concurrent migration. At the initial snapshot, run-typescript-native.ts called parseGameLog for every completed game after workers finished, but used only .neutral. The final recheck instead reads parseMatchLog and its checkpoint_game summaries. This removes the specific unnecessary full-game pass. Next, measure the saving and confirm identical totals for completed, failed, skipped and resumed games.

Worker-side completion verification: now present, still to benchmark. At the initial snapshot, verifyNativeCompletion reread and synchronously decoded all four logs in the coordinator before each receipt. The final recheck extracts that verifier into typescript-native-completion.ts and dispatches finalization through engine.verify in the engine worker. Persisted bytes and canonical hashes are still checked. This should relieve the coordinator while preserving the trust boundary, but the gain is unmeasured here. Resume still awaits verification of completed matches sequentially in the coordinator; a bounded verification pool remains relevant there. Measure event-loop delay and deadline behavior.

Reduce repeated representation changes. NativeMatchEvidence.serializeGame builds expanded typed text, then compactLog splits and rewrites it using a dictionary. The verifier expands that dictionary and constructs objects again. Generate dictionary-coded records directly from the typed event model, compute canonical hashes during serialization, and avoid multiple complete intermediate strings. The persistent worker already serializes native game evidence; finish the needed summaries and loss projection there instead of sending raw state back for another pass.

Profile copying and message volume. The worker uses structuredClone, recursive actor mapping, and evidence-size estimation on many events. Pre-side histories and complete log strings also cross the thread boundary. Consider immutable frame ownership, one actor-mapping pass, transferring encoded buffers, and compact deadline messages. Preserve hidden-information projection, seeded sideboarding histories, accurate memory limits and external per-decision deadlines. These are hypotheses to profile, not measured dominant costs.

Replace growing snapshots with journals plus checkpoints. Every completed match rewrites matches.json; each worker journal repeatedly serializes its growing owned-match list. Total serialization across a batch can grow quadratically with match count. Keep append-only durable reservation/completion events, periodic compact checkpoints and a final index. Batch metadata fsync only with an explicit crash-consistency design: a reservation must be durable before dispatch, and a completion receipt must never precede its durable files.

Make initialization and memory reuse visible. The match executor sends initialization per match, while the host caches frozen content and its adapter. This is already cheaper than recreating an engine every game. Measure cache-hit time before removing it. Keep fresh bot and duel state per game, bounded caches and a recycle policy if memory grows. Do not lower evidence fidelity or relax AI isolation to improve a throughput number.

Profile actual decisions only after orchestration is fixed. The host already measures engine, bot and projection work. Aggregate these counters. Cache repeated immutable card lookups or score components only when profiles justify it and cache keys cover the full visible game state and configuration. Changing a scoring shortcut can change gameplay; require paired behavioral verification and preserve deterministic randomness.

4.3 Evidence validation and analysis preparation: highest immediate priority

A. Cache parsed records within one verified read. In analysis-text-evidence.ts, linkedReader caches bytes, but each virtual game.json, a.json and b.json request reparses the same entire game.log. That is three full parses per game per validation pass. First-time finalizedEvidence publishes a derived receipt through validateText, then calls finalizedText, which validates again with a fresh reader. This path can parse each newly adapted game six times before generating its loss view. Cache the parsed object by verified byte hash, and carry a bounded verified result through the transaction. Do not keep all 10,000 parsed games in memory.

The read-only probe measured single-log parsing at roughly 40–93 ms for three logs of 0.83–1.91 MB. Canonical verification took 48–116 ms; loss-view conversion took 76–110 ms for two sampled losses. These are tiny warm-cache observations under active load. They support eliminating repetition; they are not population-wide averages. One unnecessary parse of 10,000 similarly sized games would imply roughly 7–16 minutes of serial work as an illustration, not an additional measured duration.

B. Extend leased byte accounting to analysis. analysis-slices.ts and prepare-analyses.ts use the generic writeOutput. It acquires a global writer lock, calls storageStatus, recursively walks the run with readdir/lstat, then stages, fsyncs and publishes one file. One measured scan of the approximately 27,410-file run took 892 ms. At that rate 5,009 scans alone would cost about 74.5 minutes; this is an extrapolation, not a profiler attribution. The active loss-view rate is consistent with a substantial scan cost.

Reuse the existing evaluation/replay lease model for an analysis scope: one reconciled reservation, local incremental counters including staging/replacement bytes, bounded child allowances, and final reconciliation. Retain 16 MB control headroom and crash-recoverable ownership. Current analysis performs at least thousands of packet/view writes, followed by two report writes per loss-bearing match; optimizing only view creation leaves the later report cost unresolved.

C. Generate target-loss views at game completion. typescript-native-worker.ts already has complete, separately mapped actor records and the terminal outcome. For a completed target loss, derive the same permitted ASCENCIO_LOSS_LOG fields from those objects before disposal. Write the full replay log and a target-only view once; publish their relationship, hashes, exact decision IDs, schema and transformation version. For wins, draws and failures, publish outcome metadata without an analyst view. Keep actor identity independent of who starts.

This moves bounded mechanical work into the existing producer pipeline, and removes the post-run full decode/encode pass. It does not make that work free. Measure any added match latency and apply backpressure. Analysis can remain blocked until all evaluation reservations settle and step 3 completes. Publishing derived evidence early does not mean starting analysts early.

D. Shrink packets to what each consumer uses. The 2,500 current match packets occupy 2.37 GB, about 950 KB per match. Discovery enumerates event references for both actors across all games, although loss-report validation uses loss games and valid decision IDs. Separate the compact loss-analysis contract from the legacy all-events contract. Keep outcomes, source hashes, loss-view references, decision indexes and exact coverage; store detailed sequence indexes once per game, or resolve them through a reader when needed. This reduces discovery memory, JSON encoding, writes and downstream rereads.

E. Shorten lock lifetimes and publish per-slice readiness. Slice sync currently converts all losses while holding withSessionLock, and only then writes the global slices.json. That blocks claims and ordinary controller transactions. Perform conversion in bounded workers outside the session lock, then briefly validate bindings and atomically publish each immutable slice. Once the evaluation barrier has passed, the first prepared slice could be analyzed while later slices prepare. Preserve ten fixed 250-match owners and reject changed inputs. This needs a transaction/state design, not removal of a live lock.

F. Do not repeat expensive integrity work at every status or report call. Discovery, packet checks, slice completion and aggregation currently traverse overlapping evidence. Establish an explicit trusted boundary: verify original bytes and schema, publish content-addressed derivatives, then verify only the needed pinned objects at each consumer. A cache keyed only by file modification time is insufficient. Across processes or resumes, check bytes against recorded hashes; within one verified immutable transaction, reuse the decode and avoid repeated hashing of the same buffer.

4.4 Analyst reasoning and consolidation

Design the log for review, not merely for machine round trips. At the snapshot, 4,121 target-loss views contain 5.075 GB, averaging 1.23 MB each. One 250-match slice has roughly 500 losses at this run's loss rate: about 616 MB at the observed average. Five sampled losses contain 844–1,801 lines, with some lines near 11,700 characters. Expanding every typed field path into a model conversation is costly and risks truncation or context overflow.

Provide a deterministic target-only review representation: card names plus stable IDs, concise visible-state changes, offered/selected choices, turn boundaries, sideboarding and results. Retain a lossless backing log and a decision/turn index for exact retrieval. Paginate by semantic boundary, not arbitrary character count. Deduplicate repeated visible state, retain complete relevant history, and expose full event detail on demand. A review-coverage ledger must show every loss was reviewed; a summary or similarity cluster cannot substitute for reviewing all losses under the current skill.

Use the existing three analyst slots effectively. Ten slices means at least four scheduling waves when only three child slots are available. Claim the next slice as soon as a slot frees. Record per-slice losses, bytes, turns and decisions to predict duration; process heavier slices first if policy permits changing dispatch order while preserving their frozen membership. Each analyst should checkpoint completed match reports inside its slice so an interrupted agent resumes uncovered work rather than rereading the entire slice. Extra analysts help only after inputs are ready and if more runtime slots actually exist.

Give all analysts one reason vocabulary and compact source context. Stable reason IDs, concise classification examples, and an explicit “unclear” category reduce later semantic merging. Use cross-slice counts of distinct games, not raw mention counts. Current draft consolidation lowercases and collapses whitespace; semantically equivalent reasons still require orchestrator reconciliation. Do not assign a cause mechanically from a signature alone, discard groups below five before merging synonyms, or treat an observed association as proof.

Make completion cheap. Validate report structure and decision references immediately, write one durable result per slice or append bounded match results, and derive presentation Markdown/JSON from that canonical result. Avoid writing and rereading identical large inputs for every report under the shared lock. Preserve the existing per-match format until its consumers are migrated together. More analytical throughput is useless if every finished slice waits minutes for storage scans.

4.5 Isolated changes and replay

Promote the existing pool through evidence, rather than building another scheduler. The experimental pool already distributes cases from all reasons over a shared queue, defaults to batch size one and separates replay calibration from match calibration. Its four-case unchanged-policy test scaled from 23.38 to 11.575 seconds at two workers, with equal replay fingerprints. That demonstrates the small fixture, not a production optimum. Integrate the pool only after verifying all cases, intended-choice changes, threshold denominators, stop behavior and source bindings through the skill's orchestration.

Remove repeated process and host startup. One pool slot currently starts a replay CLI per case; that CLI starts a fresh host for the control, then another for the alternative. Match execution's TypeScript migration does not automatically optimize this path. Extract an importable replay executor using persistent worker threads and the existing strict replay verifier. Cache engine/content per worker, but create fresh duel state, warm original policies through the recorded prefix, and create the replacement with fresh state exactly at takeover. Add leakage tests across cases and enforce external deadlines independently of a blocked worker.

Freeze and build a variant once per reason. The pool bundles transitive imports during preparation, yet the per-case CLI bundles again and reloads frozen evidence/configuration. Pass a verified prepared bundle to the executor, with complete source and runtime hashes. Cache parsed source games and paired schedules within a bounded worker cache. A loss may occur in several reasons; deduplicate its immutable input processing without conflating the different variant experiments.

Reuse identical original-policy controls. For the same source game, actor, critical decision, engine/content/runtime, original policy and takeover semantics, the control branch is independent of the isolated replacement. After one verified control, later variants can reference it rather than rerun it. Retain the exact control choice and outcome checks. Do not substitute the original recorded outcome for an unperformed control verification. Reuse across different decision points needs a separately validated contract.

Cache prefixes only with a proven engine/state contract. The highest potential replay gain is sharing validated prefix work. A generic WASM memory copy is not necessarily a complete engine/bot/RNG snapshot. First reuse immutable parsed records and prepared inputs. Then investigate supported engine checkpoints or safe replay-prefix caches, including warmed original bot state, replacement freshness, sideboarding and hidden-information projection. This is a higher-risk later optimization; it should not delay the simpler read/compile/process improvements.

Add verified replay resume and incremental accounting. The experimental pool refuses an existing output directory and has no resume. A late interruption can require manual reconstruction. Add hash-pinned case receipts and a durable journal, retain completed cases, and resubmit only eligible unstarted/interrupted work under the configured policy. Individual timeouts remain ignored and are not retried. The current child writer installation and coordinator refresh rescan a worker's accumulated files for each case; this is much better than scanning the entire run per write, but can still grow quadratically with cases per worker. Persist per-case byte deltas and reconcile once at recovery or pool boundaries.

Bound output and checkpoint work. The replay pool rewrites all rows in progress.json on each transition and hashes every case output for its receipt. Use append-only case transitions plus compact snapshots, and compute stream hashes when writing. Retain independent verification at trust boundaries. Equal fixed per-worker quotas can strand capacity behind uneven case sizes; allow safe coordinator-mediated top-ups from a shared remainder rather than increasing the global cap.

The workload is C = sum of associated losses over eligible reasons, not necessarily 5,009. A loss can belong to multiple reasons. Current fresh execution needs two branches per case. Replay every associated case; do not silently use representative sampling, top-K reasons, early success cutoffs, or drop timeouts from the denominator. A rule still requires every case to settle, the intended choice to change, and at least five wins and 5% conversion.

4.6 Decisions, history, retention and delivery

Aggregate outcomes without reconstructing timelines. aggregation-evidence.ts calls the full finalized-evidence adapter even when it later discards event lists. A verified outcome/sideboarding summary can drive weighted rates and paired comparisons. Reuse the compatible accepted-version baseline and its analysis by source, schedule, opponents and runtime identity; do not resimulate it every iteration. Keep promotion evidence distinct from isolated replay evidence.

Prevent resource transitions from becoming workflow outages. The 50 GB update had to wait for the long analysis transaction to release the session lock before its controller state could finish updating. Short transactions and a single effective configuration would avoid this split-state window. Use a managed process supervisor with durable process ownership, explicit stage events, and tested graceful interruption rather than repeated ad hoc wrappers and manual receipt reconciliation.

Maintain one authoritative progress view. The saved run.json contains current 10,000-game totals alongside stale nested budget counters from 1,020 completed games, and an earlier error string after success. These stale fields make status harder to explain and invite redundant verification. Derive user-facing status from the ledger/receipts, include its timestamp, and separate historical incidents from current state. Show evaluations completed, loss views prepared, losses reviewed and replay cases settled as four different counters.

Prune at the earliest valid boundary. Keep accepted-version and unresolved replay evidence while needed. After a rejected version is fully summarized and no longer referenced, remove its eligible details with a deletion manifest and adjust accounting once. At closure, rank saved comparable results, export the accepted AI, verify the compact summary and delete only authorized detailed artifacts. Smaller retained directories also reduce the cost of recovery scans. Increasing storage to 50 GB avoids premature exhaustion; it does not fix processing complexity.

5. Proposed faster pipeline

  1. Preflight once: resolve target and frozen inputs; validate baseline and candidate tooling support; resolve all effective limits; reuse a valid backend-specific calibration.
  2. Persistent TypeScript execution: engine workers produce authoritative records, canonical hashes, compact outcomes and target-loss views together. A bounded evidence stage verifies persisted output and publishes completion receipts.
  3. One evaluation barrier: settle reservations, verify the complete schedule, aggregate pinned outcomes and apply the baseline/candidate decision.
  4. Metadata-only analysis admission: assemble fixed 250-match slices from existing pinned loss-view references. Publish and claim each slice with a short transaction.
  5. Loss analysts: three active child slots in this runtime; compact paginated review inputs; durable per-match coverage; queue remaining slice owners immediately.
  6. Orchestrator consolidation and isolated variants: merge equivalent reasons across all slices; apply the five-distinct-loss threshold; check prior failures; freeze each variant once.
  7. One replay pool: dynamic case queue, independently calibrated concurrency, persistent engines when validated, reusable exact controls, bounded caches and resumable case receipts.
  8. Review and continuation: wait for all reason jobs. Respect the owner's current stop before combining. In a full run, combine validated edits once, validate the package, evaluate on the same paired schedule, decide and archive.

The production goal is for “evaluation complete → loss analysts can start” to become a small metadata transaction. Heavy conversion should already be complete. Work moved earlier must be included in total end-to-end timing so a faster preparation stage cannot hide a slower evaluation.

T_iteration = T_preflight + T_evaluation + T_decision + T_remaining_preparation + T_analysis + T_consolidation + T_variant_builds + T_replay + T_candidate_validation T_analysis ≈ scheduling of 10 slice durations over 3 active slots T_replay ≈ sum(case preparation + control + alternative + persistence) / effective concurrency + coordinator overhead + slow-case tail Optimize the measured largest term; do not multiply independent speedup claims.

No reliable full-run ETA exists yet. Analyst and reason workloads have not been measured in this run. At the old evaluation rate, 51 full evaluations alone would take about 164 hours; the 24-hour run limit is therefore a stopping bound, not a promise to finish 50 iterations. Even the later 200-game TypeScript rate extrapolates to roughly 54.5 minutes per 10,000 games and 46.3 hours for 51 evaluations before analysis/replay. These arithmetic scenarios are not forecasts: sustained scaling, input mix and future optimizations can change them.

7. How to prove the process became faster

Record timings at meaningful boundaries

Add structured stage events with a monotonic duration and wall-clock timestamp: run/iteration/attempt ID, source/runtime identities, worker count, completed/reused/reserved games, input/output bytes, queue depth, lock-wait time, CPU time, RSS and stop reason. Persist progress at a modest interval or meaningful transition; do not run a full directory scan every time status is displayed.

Use a representative benchmark ladder

  1. Correctness fixture: small fixed paired set with wins/losses/draws/failures, swapped starters and sideboarding. Compare complete native evidence and strict replay behavior.
  2. Performance comparison: repeated equal-work full-evidence runs in both orders at the same worker count, pinned code and no competing heavy job. Record cold and warm startup separately.
  3. Scale test: measure increasing match counts and output directory sizes. Include preparation and report completion; graph time per game and per publication as the directory grows.
  4. End-to-end baseline: a full 2,500-match workload followed by complete preparation. Measure evaluation completion → first analyst-ready slice and → all slices ready.
  5. Representative analyst pilot: one full slice with the new viewer, measured coverage and input size; audit findings before claiming a speedup. Do not infer full review time from a few easy games.
  6. Replay benchmark: short and long prefixes, different game lengths, several reasons sharing a loss, real variants, timeout/cancel/crash/resume. Calibrate replay concurrency independently.

Suggested performance gates are design targets, not current results: one parse per unique log per trust boundary; no full-run storage walk per normal publication; bounded coordinator event-loop delay; constant-size routine metadata transitions; and an analyst-admission stage dominated by small verified metadata rather than complete timeline decoding.
