pi web_search — removed, and what can replace it

What was wrong

web_search comes from pikit's web-access extension. Its search backend is hardcoded:

search.ts — uses gemini-2.5-flash-lite (hardcoded), the cheapest model in the 2.5 family that supports the google_search grounding tool. — @adrianapan/pikit/agent/extensions/web-access/README.md

Google retired that model for new users. Every call now returns:

Gemini API error: This model models/gemini-2.5-flash-lite is no longer available to new users.
Please update your code to use models/gemini-3.5-flash-lite for the latest features and improvements.

So the tool is not merely unwanted — it is dead, and pikit is at 123 weekly npm downloads, so a fix upstream is not imminent.

One consequence you should know before rebuilding

pi's settings schema has no per-tool disable. I checked Settings in pi-coding-agent-0.84.0/.../core/settings-manager.d.ts — excludeTools exists only as a CLI flag (--exclude-tools), never as a settings key. The ! syntax disables an extension file, and web-access/index.ts registers three tools in one file:

Tool Backend State after rebuild
web_search Gemini, hardcoded dead model gone — intended
fetch_content Readability + Turndown + unpdf, no API key gone — collateral
get_search_content local result store gone — collateral

fetch_content is the tool that still works; it is what I used to research this page. Unless a replacement lands in the same rebuild, you lose URL fetching and PDF extraction too.

Recommendation — pi-web-access

It is a superset of what you are losing and it answers the OpenAI half of your question directly. From its README:

Zero Config — Works out of the box with Exa MCP (no API key needed). If you're signed into Pi with a Codex subscription, OpenAI web search can reuse that auth.

Your defaultProvider in the repo settings is openai-codex, so OpenAI-backed search would work off the auth you already have — no new key, no new billing line.

It registers web_search, fetch_content and get_search_content under the same names, so it is a drop-in: fetch_content comes back, plus GitHub repo cloning, PDF extraction and YouTube/local video understanding. That name overlap is also why pikit's copy must stay disabled — running both would collide.

Caveats, stated plainly: third-party, single maintainer (nicopreme, github.com/nicobailon/pi-web-access), 32 versions since 2026-01-27, last published 2026-08-21. 106k weekly downloads is real adoption, but an extension gets tool-level access to your machine, so this is a supply-chain decision, not just a config one.

The provider-native route, if you would rather not add an extension

Both vendors now ship server-side search as a first-class API tool. Either would need a custom extension written against it — nothing off-the-shelf wires pi to them directly.

Anthropic

Server tool on the Messages API. Three versions: web_search_20250305 (basic), web_search_20260209 (dynamic filtering — Claude writes code that filters results before they hit context), web_search_20260318 (adds response_inclusion).

"tools": [{ "type": "web_search_20260318", "name": "web_search" }]

Supports max_uses, allowed_domains / blocked_domains, user_location. Citations always on, and cited_text / title / url do not count as tokens. Available on the Claude API, AWS Claude Platform and Microsoft Foundry — not on Amazon Bedrock.

OpenAI

Hosted tool on the Responses API. web_search_preview is legacy; new integrations use:

"tools": [{ "type": "web_search" }]

Supports filters (up to 100 allowed/blocked domains), search_context_size, return_token_budget, external_web_access: false for cache-only, user_location, and image results via search_content_types. Search context window is capped at 128k regardless of model context.

Cost — identical headline

Provider Per 1 000 searches Plus
Anthropic web_search $10.00 search-result tokens billed as input at model rates
OpenAI web_search (all models) $10.00 search content tokens at model rates
OpenAI web_search_preview, non-reasoning models $25.00 search content tokens free

Both require a direct API key. A Claude or Codex subscription bridge does not expose server-side tools, which is exactly why pi-web-access reusing Codex auth is the cheaper path for you.

Third option — repair rather than replace

The pikit bug is one identifier. If you would rather keep the current tool, the fix upstream is gemini-2.5-flash-lite → gemini-3.5-flash-lite in web-access/search.ts. That still needs a GEMINI_API_KEY and still leaves you on Google, so it does not satisfy the OpenAI/Anthropic half of what you asked — noting it only because it is the smallest possible change.

To install the recommendation

Not done — you asked me to search for options, not to install one. When you decide:

pi install npm:pi-web-access

That writes to the live ~/.pi/agent/settings.json, which the HM activation script overwrites on the next rebuild. To make it stick, it belongs in the repo instead — add to the packages array in dotfiles/pi/agent/settings.json:

{ "source": "npm:pi-web-access@0.24.1" }

Pinned, matching how pi-subagents, pi-claude-bridge and pikit are already pinned there.
