Real set data — sourcing, scope, fallbacks

Round 1 settled everything except one override: you want real set + rarity data for the first 50 YGO sets, now. That decision unblocks six children: which lineage “first 50” means, how the data enters a pinned offline build, and what happens where real data and the ~120-card packaged pool disagree.

feedback-vn→General UI ✓→Economy ✓→Shop ✓→Set data (Q8)
1. Which lineage is “the first 50 original sets”?

OCG (Japan, 1999, Vol.1…) and TCG (English, 2002, LOB…) have different sets, orders, names and rarities.

2. How does the data enter the build?

Project rule: assets are pinned and verified as one snapshot; the app is offline — no runtime API calls allowed.

3. Real set lists vs the ~120-card packaged pool — what shows, what drops?

Only packaged cards have art, effect text and engine scripts; a real set's list is mostly cards this build cannot render or duel with.

4. Packaged cards that appear in none of the 50 sets?

The pool contains modern-era cards (Link/Xyz etc.) that predate nothing — without a home set they become unobtainable in the shop.

5. Rarity fallback when data lacks a card?

Round 1: real printed rarity is primary. Gaps will exist (promos, data holes, the synthetic set) — something must still color the halo.

6. Where does the JSON live at runtime?

50 sets ≈ hundreds of kB — bundling it into the story JS chunk multiplies the budget bump; the budget gate reads JS bytes, not fetched assets.
