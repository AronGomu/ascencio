Four affordance surfaces

Every prompt the field can answer reaches the player through exactly one of these four. Each has one owner.

Card-anchored prompt chips

CardActionChips.svelte (src/battle/app/components/duel-field/CardActionChips.svelte) renders one button per InteractionChoice, keyboard-navigable with arrow keys/Home/End (CardActionChips.svelte:47-63). It is one implementation reused by three mount points: CardControl.svelte (hover/pin on a field or hand card, CardControl.svelte:290-298), the hand zoom overlay, and the keyboard-pinned list-entry tile.

Invisible full-cover toggle

CardControl.svelte:266-282 renders button.duel-field-card__target, data-cy="field-card-target-${card.id}". It is the sole click surface and sole keyboard-activation surface for an actionable card: pointer down/move/up/cancel handlers live on it (pointerDown/pointerMove/pointerUp, CardControl.svelte:159-233), and it carries aria-pressed for a cardSelection prompt only (aria-pressed={interactionKind === "cardSelection" ? selected : undefined}, CardControl.svelte:271).

Drag-and-drop

Pointer-only. CardControl.svelte's pointer handlers on the same target button detect an 8px move threshold (CardControl.svelte:186-192) and call up through ondragstart/ondragmove/ondragend into DuelField.startCardDrag (DuelField.svelte:573) and DuelField.endCardDrag (DuelField.svelte:825). Candidate zones come from placementZoneCandidates (src/battle/field/placement-candidates.ts:35); the dropped zone resolves back to a choice via dropChoicesForZone (src/battle/app/prompts/drop-target.ts:39).

List dialogs

ZoneListDialog.svelte runs in two modes: browse (one pile as-is) and target (only the legal off-field choices of the live prompt, ZoneListDialog.svelte:26-27). It is the sole surface for a choice addressed to hand, graveyard, deck, banished or extra deck — OFF_FIELD_TARGET_LOCATIONS (interaction-spec.ts:180-183).

Prompt families that drive the surfaces

ActiveInteractionSpec (src/battle/app/prompts/interaction-spec.ts:70-102) has six kinds, mapped from raw engine PromptKind by INTERACTION_SPEC_KINDS (interaction-spec.ts:138-160). Every choice a spec keeps lands in cardChoices, zoneChoices, stackChoices, globalChoices or offFieldChoices — the last is a T16 addition collecting any cardSelection choice addressed to an off-field location, while it also stays in its launcher map so the owning card or pile can reopen the list (interaction-spec.ts:236-243).

Both cardAction and cardSelection mark a card actionable in CardControl, but they must not render the same way. A cardAction card is being offered something to do — summon, activate, attack — resolved by one commit. A cardSelection card is being asked whether it should join a set the engine is building — a tribute, a target list — where the answer is a toggle, not a commit, and only submits once the set is complete. CardControl encodes this split today only in the accessible label (activationLabel, CardControl.svelte:65-71: "Legal action, Open actions for…" vs "Legal action, Select…") and in aria-pressed being present only for cardSelection (CardControl.svelte:271). The visual ring itself does not yet distinguish them — see § Colour and shape semantics.

Colour and shape semantics after the round

ADR-058 amends ADR-015's green/orange split. The intended end state:

Solid green ring

Legal cardAction — you may act on this now.

Dashed green

Selection candidate — you may pick this for a cardSelection set.

Dashed orange

Selected — same dashed shape, colour changed only.

Orange halo

Actionable pile — a stack offered as a legal choice.

Orange also marks the active player's rail borders under the same "current locus" reading ADR-058 gives it.

The invariant lives as a comment above the rule it governs, not in prose elsewhere: src/styles/app.css:1386-1393 currently reads "Green is the 'you may act here' colour across the field. Orange is reserved for selection below…" — the pre-round wording. ADR-058 §Decision clause 5 requires this comment be rewritten in the same commit that changes the CSS rules below it, so the comment and the rule it sits above never diverge. Full reasoning: ADR-058.

Today, verified in app.css:1395-1408: .duel-field-zone.is-actionable, .duel-field-card.is-actionable .duel-field-card__art and .duel-field-stack.is-actionable all share one solid-ring-plus-glow treatment keyed to var(--success) (= var(--legal), #7ee2a8, tokens.css:40-41). There is no dashed variant and no cardAction/cardSelection split in the CSS yet, and the active-player rail border is still teal var(--accent), not orange.

Pointer/keyboard parity

Both paths

The invisible target button is click (pointer) and native button activation (Enter/Space, keyboard) at once — CardControl.svelte:280, activate() at CardControl.svelte:224-233 tells the two apart only to decide the hand-zoom side effect, not to gate the command. Chips render for both surfaces; the list dialog's entries are buttons, reachable by keyboard.

Pointer-only

Drag has no keyboard equivalent — there is no keyboard gesture that produces a drop coordinate for zoneIdAtPoint (DuelField.svelte:839) to resolve.

The resulting rule (ADR-057 §Decision clause 4). A chip may never be deleted from the keyboard-pinned menu just because a pointer gesture now covers the same action. CardActionChips stays one implementation; only the choices array passed in from a pointer-hover call site narrows. Deleting the chip everywhere to "clean up" the duplication described below would strand keyboard-only activation on any card whose only other route is a drag. See ADR-057.

Status today: the asymmetry ADR-057 addresses — an activate choice filtered from the pointer-hover chip set (CardControl.svelte, HandZoomOverlay.svelte) but kept in the pinned menu (ZoneListEntryTile.svelte) — is decided, not yet built: no code in this repo filters activate out of any chip set today, and no hand-activation-drop-zone exists (verified: zero matches for that string under src/). endCardDrag still dispatches a lone single choice immediately regardless of action (DuelField.svelte:850-863), with no confirm step for a single-choice activate drop yet.

Materials as a card-anchored zone; local actions

Owner feedback from the 2026-08-27 round asked that Xyz materials render behind the monster like Duel Links — stacked, offset — and act as a zone in their own right: an action button opens the same list dialog any other zone uses, and an effect that detaches a material addresses it exactly like a graveyard or banished-pile target. This treats "materials attached to card X" as a fifth address space alongside the field's existing zones, not a property rendered inline on the card.

Local action is the concept this introduces and keeps distinct from a prompt choice: an affordance the field itself offers with no live engine prompt behind it — "open the materials list to look," independent of whether the engine is currently asking anything. Every surface in §1 today answers a live ActiveInteractionSpec; a look-only materials button would not, since browsing is not a choice the engine tracks in choiceOrder.

Status: decided direction, not yet a numbered ADR in this repository at the time of writing — docs/ADR/ holds no materials/local-action decision record, and no material-stacking, material-zone-list, or local-action code exists under src/battle/. Treat this section as scope description of an accepted-but-undocumented decision, not as a description of shipped behaviour.

Prompt family → affordance surface → visual treatment

Off-field cardSelection keeps its card-anchored halo as a launcher (the hand card or pile it lives on stays highlighted) while the list dialog carries the actual toggle/confirm UI — both surfaces stay live at once, per the interaction-spec's offFieldChoices dual-bookkeeping (interaction-spec.ts:236-243).
