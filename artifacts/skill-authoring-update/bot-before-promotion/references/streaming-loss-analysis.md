# Post-evaluation loss analysis

1. Wait for the entire evaluation to finish and all reservations to settle. The orchestrator verifies completion receipts and filters machine outcome metadata to identify completed target losses; no analyst starts during evaluation.
2. Partition the recorded frozen match schedule into consecutive, disjoint 250-match slices, including a smaller final slice if needed. Spawn exactly one subagent for each slice and launch them in parallel: 2,500 matches produce 10 analysts. If the runtime has fewer available agent slots, queue whole slices until slots free; keep one owner per slice and do not split or merge assignments. Derive the setup/queue `analysis-workers` capacity from the number of slices instead of the former default of three.
3. Prepare with `sync` and `maxSlices: 1`, claim and dispatch each ready slice, and continue preparation until `preparationComplete` is true. Conversion runs outside session ownership; publication uses a bounded slice transaction. The evaluation barrier still covers every scheduled match before the first slice becomes ready. For each slice, pin the evaluation, AI version, match range, packet identities and source hashes. Supply an explicit allowlist containing only that slice’s projected target-loss view logs. The slice preparer copies only the target actor’s visible content for a lost game into its loss view; analysts receive no full two-actor game file. They must not open win/draw game files or read their gameplay, nor read timeout/failed/skipped game files. A match index may be used only for references; no traversal into non-loss games. Accepted-version winning-game logs are also excluded. The orchestrator may supply paired outcome flags derived from metadata, without supplying winning-game content.
4. Read every ordered `loss.review.pages` page, or its complete allowlisted `loss.log` fallback. Review pages preserve all events and decisions, retain choice labels/card identities, and express repeated non-decision state as changes since the previous event of the same kind. Pages share one Markdown file per loss; each allowlisted page carries a byte offset, byte length and digest, plus event/decision counts. Read a bounded page with `node scripts/bot-improvement/loss-review.ts SESSION PACKET_PATH PACKET_SHA MATCH GAME PAGE` (page numbers start at 1). The helper verifies the packet and page bytes. Page hashes and event/decision counts bind them to the loss log. Record review duration and supplied bytes; pagination must never silently truncate coverage. Each analyst diagnoses game-loss reasons only; it neither implements AI changes nor runs replay/evaluation jobs. Preserve the current Markdown findings format below, with one row per target loss and separate job/packet bindings for each match. During the first review capture the primary classification and every supported secondary reason with a stable reason ID, exact decision ID and complete ordered offered/chosen choice IDs. Use the structured `findings` submission below to generate the per-match Markdown mechanically. Checkpoint completed match findings in small batches under the current claim token. Resume only packet jobs absent from `claim.completedJobs`; completed findings survive release and reassignment. Return slice coverage to the orchestrator. This is one analyst processing up to 250 matches, not one new analyst per match. A slice without losses reports zero losses reviewed and opens no game logs. Keep single-occurrence findings; apply no five-loss cutoff within a slice.
5. Reuse findings only when identities and hashes match. The orchestrator validates returned game/decision IDs against the allowlisted source loss records, checks that every completed target loss is covered exactly once across slices and reconciles overlapping reason categories. Timed-out games remain ignored incidents with bug reports, not loss reasons.
6. Wait for every slice to finish before compiling one `baseline/loss-analysis.md` or `iterations/iteration-N/loss-analysis.md` using [loss-analysis-template.md](loss-analysis-template.md). Merge equivalent reasons across all slices, rank by distinct affected losses and retain all groups meeting the global five-loss threshold. Record unclear losses and coverage. Slice reports do not independently trigger AI changes. After the single document is complete, continue the skill’s normal replay, candidate preparation and evaluation workflow.
7. On owner stop or execution failure, stop dispatch and settle or terminate owned analysts. Preserve completed reports, slice ownership and unfinished loss coverage for explicit continuation; resume uncovered work without duplicate analysts. Keep action logs until analysis delivery and reason replay review, honoring owner retention requests.

Use the authoritative lossless game logs. The frozen pool writes them automatically; discovery publishes their native completion receipts after verifying the outer match is closed. For standalone producers, run [publish-text-match.ts](../../../../scripts/bot-improvement/publish-text-match.ts) after the native writer closes each match. The script verifies the typed log records and publishes its completion receipt; it generates no XML or games.

Use [analysis-slices.ts](../../../../scripts/bot-improvement/analysis-slices.ts) through `npm run bot:analysis-slices -- SESSION REQUEST.json`:
- `{"action":"sync","binding":...,"maxSlices":1}` verifies all matches are finalized, derives consecutive 250-match slices and publishes at most one new slice and returns `preparationComplete`. Repeat while dispatching ready slices after the full evaluation barrier. Omitting `maxSlices` prepares all remaining slices. Native workers supply verified target-loss views; legacy sources use the equivalent projection.
- `{"action":"claim","iteration":N,"role":"candidate","owner":"analyst-id"}` returns one whole slice. Spawn one agent per slice packet; slots beyond runtime capacity wait without changing assignments. An owner retry returns its existing claim.
- The analyst submits complete first-pass structured findings (or compatible existing per-match Markdown reports) for each `packet.jobs` entry, using its job ID and packet SHA; it reads only the packet’s review pages and target-loss logs. A no-loss slice returns an empty report list without opening game logs.
- `{"action":"complete","iteration":N,"role":"candidate","slice":"slice-0001","token":"...","reports":[{"path":"...","sha256":"..."}]}` validates complete loss coverage and publishes the existing per-match findings and code-generated analysis metadata. `release` requires the slice ID, claim token and `terminated:true`; reassignment invalidates old completions.
- `{"action":"checkpoint","iteration":N,"role":"candidate","slice":"slice-0001","token":"...","findings":[...]}` validates and saves any completed match subset without releasing the owner. `complete` accepts the remaining subset (or an empty list once all jobs were checkpointed). A changed previously accepted report is rejected; identical retries are safe. Old `reports` reference submissions remain supported.
- `status` reads saved metadata/summary only and does not certify current source integrity. Use `audit` before relying on a resumed completed analysis for rule work: it verifies source/report/page bytes and coverage. Audit also creates a saved summary for completed legacy slices that predate cached summaries.
- Once every slice completes, the tool creates a merged `loss-analysis-draft.md`. The orchestrator reconciles semantically equivalent reasons across slices and writes the one final `loss-analysis.md` in the baseline/iteration location, then resumes the normal workflow. Five-loss eligibility is evaluated globally, never per slice.

The underlying [prepare-analyses.ts](../../../../scripts/bot-improvement/prepare-analyses.ts) queue and packet schema remain the match-level validation/archive interface. The slice layer owns analyst dispatch; do not mix independent per-match claims with slice claims. Setup derives analyst capacity from slice count. JSON here stores control/analysis metadata only, never game timelines or per-game actor records.

```markdown
# Match loss analysis

Job: <packet job ID>
Packet: <packet SHA-256>

- G1 | 0-decision-42 | avoidable | Wrong destruction target | Prefer opposing backrow
- G3 | - | unclear | No supported decisive error | Review similar losses
```

Write one row per target loss, with fields separated by `|`; use no pipes inside fields. Classifications are `avoidable`, `unavoidable` or `unclear`. An avoidable finding needs a decision ID present in that lost game's target record. Use `-` for an unavailable decision. The queue rejects wrong bindings, winning-game findings, duplicate losses, invented decisions and incomplete coverage. Human/agent-facing findings and the final report remain Markdown. These per-match files and structured records are temporary: consolidate their counts and findings into the run-level summary, then remove them at run closure under the skill’s Output retention rules.

For a regressing combined candidate, the orchestrator compares paired outcome metadata and flags newly introduced losses. Analysts read only candidate loss content and identify added rules implicated by its recorded choices; winning/drawing accepted-game content stays excluded. Rank suspect rules by supported affected-loss count and test each isolated removal/update against the unchanged regressing candidate using exactly the same all-case replay and 5-wins/5% thresholds as new fixes; do not claim causation from association alone.

## First-pass findings submission

Each `findings` entry has `schemaVersion: 1`, `format: "loss-markdown-v1"`, `job`, `packetSha256`, the existing `findings` rows (one per target loss), and a required `reasons` array. Each reason has `game`, stable kebab-case `id`, `decision`, ordered `offered` and `chosen` choice-ID arrays, `reason`, and `solution`. Include the primary avoidable finding and all supported secondary hypotheses; use `reasons: []` when none are supported. Use one critical decision per game/reason. These remain hypotheses until counterfactual replay validates them. Keep activation and target-selection reasons separate. Reconcile synonymous IDs across slices before applying the global threshold.

The tool generates Markdown primary rows and `- R G1 | reason-id | decision-id | ["offered-id"] | ["chosen-id"] | Reason | Solution | supported` rows under `Reasons: complete`. It validates every reason against the pinned decision’s actual offered/chosen IDs. Escape pipes in JSON choice IDs as `\u007c`; prose fields stay single-line without pipes. One loss may support several reasons, but primary coverage counts it once and each reason’s threshold counts distinct games.
