Duel Field Interaction Model v2

How a prompt becomes something you can click, after the round-2 feedback. Adds three things the v1 shell did not have: pile contents as first-class interaction targets, a projected deck order with reveal tracking, and a client-side policy for prompts that are not decisions. Supersedes the interaction sections of duel-field-interaction-shell.html wherever the two disagree.

Prompt pipeline

Unchanged in shape, widened in the middle. The engine still owns legality; the field only expresses it.

The rules layer never moves. Every addition below is presentation resolving which pixel expresses a choice the engine already offered. Presentation state still never gates legality.

Four target kinds

KindProduced whenRendered byClick does
cardChoiceschoice targets a mounted card (hand, monster, spell/trap, field) CardControl one choice → fire it; several → open the chip row
zoneChoiceschoice carries a place ZoneControl single-place prompt → submit directly; otherwise toggle
stackChoiceschoice targets a card in deck / extra / graveyard / banished StackControl halo + ZoneListDialog open the pile's list; act on a card inside it
globalChoicesno field target at all (pass, endPhase, battlePhase, …) FieldActionBar, PhaseStrip, EndTurnButton fire the choice

Why a pile choice cannot be matched by id

sanitizeChoice reduces a choice to { id, label, action, value?, toggleState?, allocationMaximum? } — the card is gone. And PromptChoice.card.instanceId is not the projector's instance id: the protocol layer synthesises p{controller}-l{location}-s{sequence}. The only reliable join is the address triple, so InteractionChoice carries cardAddress: { controller, location, sequence } and the list dialog filters on it.

Ordering trap. stackChoices must not count toward fieldCapable until the list dialog exists. Flip it early and a graveyard activation is unanswerable — the modal hides, the field has nothing to click, the duel deadlocks.

Surface routing

promptSurface(prompt, spec, showWorkspace)
  prompt === null                    → "none"
  showWorkspace                      → "docked"     (dev workspace panel)
  prompt.kind === "chain"            → "field"      ← NEW: chains never modal
  spec.fieldCapable                  → "field"
  otherwise                          → "dialog"

fieldCapable = cardChoices.size > 0 || zoneChoices.size > 0 || stackChoices.size > 0. A chain is forced to "field" unconditionally so a source the mapper cannot place still cannot resurrect the modal. The chain question lives in the preview panel's status line — "Do you respond?" with three pulsing dots, suppressed under prefers-reduced-motion.

Passing versus cancelling

promptControlFamily("chain") === "single", and validatePromptSelection rejects an empty response for a single-family prompt even when it is cancelable. So a click on empty field means two different things depending on the prompt:

  • chain → submit the pass choice. A forced chain has no pass, so the click is inert and the player must answer.
  • multiple/order family, cancelable → submit an empty selection (a real cancel).
  • anything else → inert.

Automatic resolution

Two in-memory session settings, both on by default. Both policies are pure functions of the prompt, so both are unit-testable without a duel.

autoResolveTrivialPrompts

Answers a chain with only pass; a forced chain with exactly one choice; an option with one choice; a selectPosition with one choice. Requires player === 0 and a one-of-many shape.

autoPlaceCards

Answers a selectPlace with min === max === 1 using the most central offered place. Rank [2, 1, 3, 0, 4]; extra monster zones after every main sequence, 5 before 6; player 0 before player 1; ties on choice id.

Resolution fires once per prompt id, from a reactive statement, never while a response is in flight. selectDisabledField is excluded despite sharing the placeSelection spec kind — it is targeting, not placement.

Precedence is free. The drag-drop pendingPlacement intent answers from inside the worker-client subscription, so responsePending is already true when the auto-resolution statement runs. A deliberate drop always beats the automatic centre.

Deck order & reveals

The projector does not model deck contents. It keeps deckReveals: Map<offsetFromTop, CardCode> per player and synthesises PublicPlayerState.deck at snapshot time from deckCount plus that map. Index 0 is the top.

Engine messageEffect on revealsWhy it is safe
DRAWshift every reveal down by drawn.lengthcards leave the top; no sequence involved
CONFIRM_DECKTOP (30)reveal offsets 0..n-1cards[i] is the i-th from the top
DECK_TOP (38)reveal offset countcount is already an offset from the top
SHUFFLE_DECK (32)clearorder destroyed or untrackable — forget rather than guess
SWAP_GRAVE_DECK (35)clear
REVERSE_DECK (37)clear
MOVE touching a deckclear
CONFIRM_CARDS (31)ignoredits entries carry engine deck sequences — the ambiguity we are avoiding

The safety asymmetry. The projection may forget a reveal. It can never invent one. Every future change to this map must preserve that, and every clear-on-doubt above exists for it.

Slot shape

unrevealed  { instanceId: "deck-p0-7", location: "deck", sequence: 7,
              position: "faceDownAttack", faceUp: false }          // no code

revealed    { instanceId: "deck-p0-0", location: "deck", sequence: 0,
              code: 12345, position: "faceUpAttack", faceUp: true }

faceUp is what carries visibility downstream, and it is also what keeps the contract validator's opponent face-down implies no code rule satisfied for a legitimately revealed opponent deck card.

Foot-gun. isCardIdentityVisible(0, 0, "deck", …) returns true — its first disjunct is controller === viewer. Using it for deck entries would reveal your whole deck. Deck entries read faceUp && code !== undefined instead.

The deck pile on the board still shows no art. publicCards.at(-1) on a deck is the deepest revealed card, not the top one, and only graveyard and banished were asked for.

Field overlays

The board's geometry is fixed by duel-field-layout.ts. One horizontal band — y 51%–64% — is free of every zone except the two shared extra monster zones at x 46.1%–60.3%. Overlays live there or outside the zone extents. Nowhere else.

OverlayPlacementPointer rule
PhaseStripfree band, split by the EMZscontainer none; only offered chips auto
EndTurnButtonright: 1%; top: 57.5%, between the banished pilesalways auto, outside every zone
FieldActionBarpinned bottom, board padding reserved for itboard padding carves its footprint out of the hit area
ZoneListDialogcentred on the board, max 80% × 70%no backdrop — must never block the field
CardActionChipsabove the hovered card, overlapping 0.35remrevealed on hover / focus-within only

History, not theory: a field bar painted over card targets once cost a full session and 344 retried Playwright clicks. The chromium responsive-composition spec is the standing gate. If it fails, move the overlay — never relax the assertion.

Privacy invariants

  • Opponent hidden information is stripped in the worker, before the clone boundary. The UI re-checks anyway; both layers are load-bearing.
  • A face-down card in state.players[1] must carry no code. The contract validator enforces it. Revealed deck slots satisfy it by being faceUpAttack.
  • Zone list entries derive visibility per zone: graveyard, banished and extra deck through isCardIdentityVisible; deck through faceUp && code. Never a blanket rule.
  • A hidden card previews as "Face-down card" with no text and no image lease. It never leaks a code through the preview path.
  • The opponent's extra deck and deck list as face-down entries with a position number and nothing else. Position is public; identity is not.
