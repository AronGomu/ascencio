# Explanation from review-b for fresh comprehension of the pending-rule skill

## 1. Outcome and scope

Improve the supplied target `ai-bot` through reproducible paired-game evaluation against frozen starting self-opponent plus optional opponents; deliver accepted source, verified results and compact history, including an honest unchanged outcome. Owner limits and a compatible checkpoint are optional inputs. Only target AI changes; decks, engine, legality and hidden-information boundaries remain protected. Push, publish and merge require separate authorization.

## 2. Process overview

The orchestrator implements; delegated analysts diagnose target losses. The stateless controller prints stages and checks edges while project tools own execution and durable state. Preparation pins identities, limits and two calibrations; baseline/candidate evaluation leads through a persisted decision and mandatory analysis. Authorized further work replays isolated fixes, assembles passing rules and repeats evaluation. No qualifying rule or the decision ceiling leads to delivery; resource and incident stops override all progression. Pending rules survive ordinary attempts and require fresh replay against each current analysis source.

## 4. Identities and invariants

| Item | Initial source/value | Allowed changes | Must remain fixed | Verification |
|---|---|---|---|---|
| Paired comparison | Pinned setup/opponent order/schedule | Candidate policy may alter trajectories; accepted reference moves only on promotion | Deck orders, engine seeds, sides, rules/content; stable match/game randomness; frozen opponents including starting AI | Hash/source/settings/schedule/integrity match; ignore either paired side from both rates; draws count zero wins in denominator; each opponent has a completed pair |
| Ordinary source mode | Baseline, accepted candidate, tie or unassessable rejection | One added fix per isolated variant | Analysis/control/assembly use accepted source; rejected evaluation analyzed before returning to accepted analysis | Separate accepted commit, replay source and assembly base recorded |
| Regression repair mode | Valid lower-rate candidate | Remove/update one existing rule; add none | Analysis/control/assembly use regressing candidate; preserve unedited rules; comparator remains accepted | Candidate-loss-only diagnosis; paired metadata flags new losses; implicated rules ranked by distinct supported losses, association not causation |
| Pending rule | Stable reason/rule IDs, aliases, semantic rule/source hash and original provenance | Explicit reconciliation of similar losses; materially different correction gets new identity and explanation | Separate corrective rules stay separate; deterministic first-seen distinct losses capped at 300; repetitions add no cases | Retain findings, loss/source/log hashes, decisions, offered/chosen IDs, attempt outcomes |
| Current-source replay | Every accumulated case's original pinned inputs | Fresh unchanged-current-source and current-plus-rule branches every subsequent iteration | All old and new cases retested; historical results never substitute; historical prefixes cannot force old-policy control choices | Reconstruction, legal decision addressing and applicability established; otherwise blocked, not a non-conversion/rejection |
| Terminal rule status | Complete valid current-source replay of 300 distinct cases | New materially different rule can be attempted | Below either conversion threshold at cap → exact rule proven-discarded, durable failed history; below cap → pending | Record denominator/counts/source/rule/evidence; resource/interruption/integrity stops never prove discard |
| Representation/version | campaign/round/incumbent API names; typed lossless .log | Tool-generated JSON metadata; tool-generated Markdown findings | No gameplay JSON sidecars, no legacy adaptation, no protected changes | Exact IDs/nulls/ordering preserved; programmatic full logs, analyst target-only loss projections |
