The bug that produced both decisions

A duel ended with ocgcore rejected the previous response and nothing else. The trace tail:

474  message  type 143   ANNOUNCE_NUMBER
475  prompt   …-prompt-149  player 1
476  response choice-0-select  opponentReason: select_first_legal
478  message  type 1     MSG_RETRY
479  error    ocgcore rejected the previous response
480  lifecycle session_closed:failed

The registry answered with the announced value:

value: Number(message.options[exactlyOne(ids, bindings).rawIndex])

ocgcore reads that field as an index into its own option list and retries when it is out of range. The vendored writer confirms it takes the integer raw — case 19: t.i32(e.value) — so nothing in between could have corrected it.

An option list of [1, 2, 3] answers correctly by accident. [4, 6, 8] kills the duel.

Contract: what each response field means

The TypeScript types cannot distinguish these — { type; value: number } looks identical either way — so each encoder states its semantics in a comment and is pinned by a test built from values that differ from their positions.

Authority for every row: vendor/ocgcore-wasm/0.1.2/dist/index.d.ts plus the response writer switch in dist/index.js. A prompt kind without an encoding test is not finished.

Recovery: replay, not snapshot

The frozen core exposes no state snapshot. What exists is a trace that already records the seed, the deck selection and every prompt/response pair — and an integration harness that already replays exactly that.

Why the stop point is the last human decision

  • Replaying opponent answers verbatim reproduces the exact position rather than letting the policy re-decide into a different game.
  • Stopping at your own last decision gives you a real choice again — including a different line that routes around an unfixed bug.
  • Cost is a full replay of the duel so far: linear in the duel's length, milliseconds at duel scale, and exact because the same seed and the same recorded answers produce the same core state.
  • This is recovery, not undo. It is reachable from the error dialog only; an in-duel undo would raise rules-integrity questions this decision does not answer.
